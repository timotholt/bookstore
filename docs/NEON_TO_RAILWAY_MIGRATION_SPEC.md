# Chantel’s Corner PostgreSQL migration

Status: production cutover completed on 2026-11-04. See the execution evidence below. The original Neon database is retained and fenced during observation.

## Scope and success criteria

Move the complete storefront PostgreSQL database from Neon to a private PostgreSQL 18 service in the same Railway project, production environment, and region as the web service. Keep the storefront deployment revision fixed during the move. The production switch is a Railway **web service** variable change and redeploy. The ignored local `.env` only affects local commands and development.

Preserve all application schemas, rows, schema objects, sequence positions, and migration history. The last committed source transaction before the write freeze must exist at the destination. Start serving Railway only after the final parity check and record the point at which Railway becomes authoritative. Keep an encrypted, independently recoverable archive and a tested path to restore service.

A read-only probe of the locally configured Neon database found PostgreSQL 18.6, 135 MB on disk, `public` and `tower_sessions` tables, and only the standard `plpgsql` extension. Confirm those observations against the actual live database before using them. Production’s database identity and Railway’s incremental monthly cost are open items. Neon currently costs approximately $10–$11/month. Compare that with the incremental workspace bill including backups, using representative usage measurements from the rehearsal.

## Preflight

- Identify the Railway web service, production environment, deployed commit and image, all deployment domains, and the live database branch, endpoint and database name. Compare the resolved runtime `DATABASE_URL` privately with Neon Console. A masked host plus database name, service and branch IDs, and deployment ID are enough for the operator record. Check for additional application databases, clients, background jobs, subscriptions, provider webhooks, and operator tools. Each additional database needs its own scoped plan.
- Inventory extensions and versions, schemas, tables (including partitions and unlogged tables), sequences, large objects, materialized views, policies, triggers, functions, foreign servers, replication objects, role membership, object ownership, grants/default grants, and database-level settings. Check encoding, locale, collation provider and version, and time zone. Match compatible settings on the target and exercise search/sorting. Inventory application role requirements, including whether it needs DDL for startup. Resolve provider-specific dependencies and any ownership-sensitive function or policy before rehearsal.
- Install or explicitly select PostgreSQL **18** client binaries. The Mac’s default `pg_dump` was 16 and cannot export a PG18 server. Use the same verified client set for both directions. Verify the destination’s major version and free disk. Leave headroom for indexes, restore WAL, and backup operation.
- Create a scratch PostgreSQL 18 service for rehearsal. Scope it to isolated access. Test the intended production private connection in a rehearsal app with equivalent configuration, using `EMAIL_PROVIDER=disabled` or non-production capture and no real payment/webhook credentials. Production rejects capture. Confirm the rehearsal cannot send mail or receive live webhooks. Restrict access to the clone and remove it after evidence is captured.
- Choose an operator for each phase and agree the downtime and abort deadline from timed rehearsal. Pause automatic deploys and operator jobs at cutover. In the Deployments view, remove active deployments and abort queued or in-flight builds for each writer. Verify every replica is stopped. Inventory how to block every public route, including Railway-generated URLs and webhook endpoints. If a maintenance responder is unavailable, use a planned outage with every app replica stopped. Test the actual Railway controls, the restore privileges, and the ability to restart the pinned deployment with the previous configuration.

## Archive and restore procedure

Use Neon’s **direct** endpoint and a role that can read the entire application database, including tables protected by row-level security. Use explicit verified TLS settings where supported and an out-of-repo, permission-restricted libpq service file/password file or equivalent secret injection. Configure libpq aliases for the exact source and destination, and confirm server identity separately in each session. Never paste raw connection URLs into command history, put them in the operator record, or log table contents. For a Mac restore, use an encrypted temporary Railway TCP proxy connection and remove the proxy after import. A private in-project restore runner is also suitable.

Keep an encrypted archive in owner-controlled storage separate from both providers. Restrict the folder and artifact to the operator. Use a new path per attempt and retain the failed attempt logs privately. These commands assume aliases and an empty target already verified, and should run in a shell that stops on errors:

```sh
set -eu
umask 077
: "${ARCHIVE:?Set a unique path on an encrypted volume outside the repo}"
test ! -e "$ARCHIVE"

pg_dump --dbname='service=chantel_neon_direct' --format=custom --compress=gzip:6 --verbose --file="$ARCHIVE"
pg_restore --list "$ARCHIVE" > "${ARCHIVE}.toc"
shasum -a 256 "$ARCHIVE" > "${ARCHIVE}.sha256"
shasum -a 256 -c "${ARCHIVE}.sha256"

pg_restore --dbname='service=chantel_railway_restore' --single-transaction --exit-on-error \
  --no-owner --no-acl --verbose "$ARCHIVE"
```

Use a full database dump with no schema or table filters. Compare the archive inventory against the source. This includes `public._sqlx_migrations`, `tower_sessions`, the catalog, authentication and staff data, reviews and moderation history, carts and saved items, email state and analytics. A logical database archive does not provision cluster roles, provider configuration, or other databases. Retain the original ownership and ACL metadata in the archive and separately record role/privilege requirements without secrets. Restore under the planned application-object owner and apply a reviewed Railway role/grant mapping, including any schema grants or policy dependencies. Apply approved database- and role-level settings explicitly, since the restore does not use `--create`. Keep provider administrator access separate from runtime credentials. Verify startup migrations and session initialization with the actual runtime role. If administrative privileges are required for extensions or other objects, install those prerequisites and rehearse the ownership handoff explicitly.

Restore into a fresh database created with the confirmed locale/encoding. Never run cleanup against an existing live database. A failed restore is a stop signal. Preserve its logs, correct the cause, and retry on a clean target. Run `ANALYZE` on the restored database before testing catalog performance. Test restoring the encrypted archive independently, and document its checksum, retention, key access, and recovery steps.

## Validation and evidence

- During rehearsal, take source fingerprints and the dump from one consistent snapshot. Export a snapshot from a read-only repeatable-read transaction, keep that connection open, and pass the snapshot to `pg_dump --snapshot`. Obtain sequence values during a writer freeze for final equality because sequence state is outside MVCC. At cutover, the proven write fence keeps the source stable through both the archive and the comparison.
- Enumerate every application table from the catalogs and compare exact row counts and SHA-256 fingerprints of a deterministic row stream. Use identical client/serialization settings and explicit stable ordering, including a deterministic full-row ordering for tables without keys. Compute hashes in trusted processes and retain only results. Compare sequence values and called flags, migration versions/checksums, large objects if present, and normalized schema definitions including indexes, constraints, policies, and triggers. Account explicitly for intended ownership/ACL differences. Zero unexplained differences are allowed.
- Verify the pinned build starts with the restored migration ledger, `/readyz` succeeds, and the app is connected to Railway. Before startup, verify that the pinned binary’s embedded migration versions and checksums exactly match the restored SQLx ledger, with no pending migrations. In rehearsal, exercise catalog search and book pages, sign-in, a cart and saved item, review submission and moderation, staff authorization, checkout pause, and captured email/outbox handling. Use a known test account in rehearsal. Compare the final production database before any mutating smoke tests. Record both app behavior and database evidence.
- Time dump, restore, validation, app start and a return to Neon. Rehearse a reverse restore into an empty Neon database or branch using disposable data and verify parity. Measure storage and steady-state memory/CPU using representative workload. Test an independent restore from the Railway backup strategy before retiring Neon.

## Production switch

1. Set maintenance across every ingress and verify it from outside Railway. Return a retryable failure to `/webhooks/resend` and prove with a test event that Resend retries or that an operator can replay deliveries during the window. Never acknowledge an event the storefront did not process. Quiesce the email outbox and record pending/sending work and any ambiguous external deliveries. Preserve outbox IDs and leases. Reconcile uncertain sends against the provider before starting the new worker. Stop the old web deployment, all replicas and workers, and any external writer. Ordinary Railway redeploys can overlap, so a variable redeploy alone is insufficient as a write fence.
2. Apply the rehearsed source-side fence to the runtime and job identities, terminate their existing database sessions after drain, and prove they cannot reconnect/write. Include login roles that inherit or can assume writer or owner roles. Keep a separate backup/operator identity. If the current app shares the owner identity, rehearse an owner-safe fence before the window, such as isolating the backup identity and disabling the app’s old login or rotating its credential and terminating sessions. Recheck active clients and jobs in `pg_stat_activity` using an identity with adequate visibility. A read-only session default or revoking ordinary table privileges from the owner does not enforce this fence. A maintenance page or checkout pause alone is insufficient. Abort if all writers cannot be fenced.
3. Take the final full archive after the fence. Verify its checksum and restore to the clean production Railway database. Apply the audited role mapping, verify all parity checks, and confirm target backup configuration. With the deadline approaching or any check failing, follow the rollback section.
4. In Railway, open the **production web service → Variables**. Save the old connection configuration securely for rollback. Change `DATABASE_URL` to a private reference such as `${{Postgres.DATABASE_URL}}` if the service is named `Postgres` and its URL uses the intended app role. If the generated URL uses the provider admin account, supply a private app-role connection URL as a secret instead. Set `EMAIL_PROVIDER=disabled` for the fenced startup. Preserve the exact `EMAIL_OUTBOX_KEY` and `EMAIL_OUTBOX_KEY_ID` so the new worker can decrypt existing queued messages. Save the original email provider setting for re-enable and rollback. Apply only the planned changes and redeploy the pinned revision. Verify the resolved private host and database, migration startup, and readiness. Recheck the data after the fenced boot and explain any initialization-only changes before enabling production writes. If ingress cannot stay blocked during a production deploy, rehearse a private health probe and mark Railway authoritative before deploying the live build.
5. Keep public ingress fenced until verification passes. Block operator writes and mutating smoke tests during this phase. Even browser GETs may write session state. Startup can execute migration/session initialization SQL, so compare before startup and recheck after it. Any unexpected persistent change blocks opening traffic. The current app starts the email worker during startup. Treat the first production worker action or external delivery as potentially crossing the rollback boundary, even with ingress blocked. The code returns before polling when `EMAIL_PROVIDER=disabled`. Confirm this with the pinned build during rehearsal. Verify migration startup, database identity, and readiness with email disabled and public ingress fenced. Verify the old deployment is stopped before the new app receives traffic.
6. Mark Railway authoritative in the log immediately before restoring the original email provider and redeploying the pinned build against Railway. Keep ingress fenced until that deployment is ready and the disabled-email deployment is stopped. Reopen ingress. Check health, the catalog and staff/account/review workflows, database connections and errors, and webhook/outbox reconciliation. Keep Neon fenced from app writes. Disable temporary public database access. Track Railway usage and backup status through the observation window.

## Rollback and retirement

**Before Railway is authoritative:** keep ingress fenced, stop the target app, restore the prior `DATABASE_URL`, original email provider setting, and valid source credentials, lift the Neon writer fence deliberately, then redeploy the pinned revision. Verify it connects to Neon and reopen ingress. Preserve the target for diagnosis.

**After Railway is authoritative:** keep Railway as the source of truth. Prefer a forward repair or restore within Railway. For a return to Neon, fence Railway writers and workers, archive the latest Railway state, restore into a fresh Neon target with verified compatibility and role mapping, validate full parity, reconcile external mail/webhook effects, and perform a second controlled cutover. The original Neon database is a pre-cutover snapshot. Track the effects of any backup recovery point that precedes the failure.

Keep the original Neon database and the encrypted cutover archive until the agreed observation window ends, parity and backup restores have passed, and the new Railway costs are confirmed. Default proposal is daily Railway backups plus an encrypted off-provider logical backup, with recovery-point and recovery-time targets agreed before cutover. Decide whether Railway point-in-time recovery is needed if a daily recovery point is too old. Allow seven days of operational observation and an explicit owner decision on archive retention and Neon retirement. Review Neon-specific spend monitoring before revoking credentials or retiring the project. Update operational documentation and local development configuration only after the production switch is accepted.

## Rehearsal evidence, 2026-11-04

- The live Railway web service points to `chantels_corner_demo` on the Neon `bookstore` production branch. Restored the full 8,321,531-byte archive to the [private Railway rehearsal project](https://railway.com/project/966c6325-905c-4e9f-bbbf-aa73e0c8fc7a). The dump took 9.1 seconds and the restore took 6.5 seconds. All 38 table counts and content hashes, 16 sequences, and normalized schema matched. The encrypted Mac volume holds the restricted local archive. Off-provider archive recovery and Railway backup restore remain cutover gates.
- Built production revision `185703c45cf023087edd304475264878476f1893` on the Mac and connected through a loopback SSH tunnel to the Railway copy. With email disabled, production-mode readiness and all 22 migration checksums passed. The localhost HTTP smoke verified the catalog, sign-in with synthetic fixtures, persistent cart and saved items, checkout HTTP 409, pending review visibility, and ordinary user/moderator access boundaries. Signup intentionally refused account creation with email disabled, and the outbox fingerprint was unchanged.
- A data-only role failed startup first on `public` schema CREATE and then on database CREATE. The successful role used CONNECT, schema USAGE, sequence USAGE/SELECT, application DML, and CREATE on the database plus the `public` and `tower_sessions` schemas. Catalog and migration ledger remained read-only to the app role. The login had no cluster admin privileges. Future schema migrations require a separate owner/operator step under this grant model. The rehearsal role is now NOLOGIN and its password and temporary SSH access were removed.
- Eleven Railway samples over five minutes averaged 0.254 GB memory, 0.00185 vCPU and 0.249 GB volume use. At published rates this is roughly $2.61/month in database resource usage if sustained, before backup or additional egress. This is a short rehearsal estimate. The production build ran locally, so the sample measures the Railway database service. The separate private database remains online and continues to accrue usage.

## Production execution, 2026-11-04

- Confirmed the Neon source and deployed revision `185703c45cf023087edd304475264878476f1893`.
